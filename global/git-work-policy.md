# Git Work Policy

AI Context Harness を利用する AI エージェントの、Git / GitHub 作業に関する共通ルール。

## 1. Completion Principle

意味のあるコード・ドキュメント変更を行った場合、作業完了の基本単位は以下とする。

`変更 → 検証 → commit → GitHub反映確認`

ローカルに commit が存在するだけでは、GitHubへの反映完了とは扱わない。

## 2. GitHub反映の優先順位

1. 現在の実行環境で `git push` が利用可能なら、通常の Git 操作で push する。
2. `git push` がネットワーク・認証・サンドボックス制約で失敗した場合、利用可能な GitHub 連携/API 経路を使用して、同じ変更を GitHub 側へ反映する。
3. いずれの経路でも反映できない場合は、作業を「Push済み」と報告してはならない。
4. commit 済み・Push 未完了の場合は、その状態を明示し、commit SHA と失敗理由を報告する。

## 3. Push前確認

- 対象リポジトリが正しいことを確認する。
- 対象ブランチが正しいことを確認する。
- 作業ツリーと差分を確認する。
- 必要なテスト・lint等を実行する。
- secrets、credentials、個人情報、機密情報を含む変更を反映しない。
- 原則として force push は行わない。

## 4. GitHub連携経路を使用する場合

GitHub連携/APIで反映する場合も、通常の Git commit と同じ意味になるように扱う。

- 対象ブランチの最新HEADを確認する。
- 変更対象だけを反映する。
- 反映後にGitHub上のHEADまたはcommitを確認する。
- 反映確認できるまで「Push完了」と判断しない。

## 5. 実行環境の違い

GitHubコネクタ接続と、実行コンテナ内の `git` / `gh` 認証・ネットワークは別経路である場合がある。

したがって、以下を混同してはならない。

- GitHub連携が接続済みであること
- ローカルシェルから `git push` できること
- GitHub側へ変更が実際に反映されたこと

## 6. 複数セッションでの標準動作

ChatGPT、Codex等の実行環境が異なっても、本ポリシーを共通ルールとして適用する。

各セッションでは、可能な経路を使って最後までGitHub反映を試行し、結果を事実ベースで報告する。
